Veilkeeper · Architecture case study

One combat execution path. Human and AI controllers.

Separating action selection from combat execution lets different controllers use consistent gameplay rules—and makes complete matches available to automated smoke testing.

1. Problem and requirements

Veilkeeper needs both a person and an AI to drive turn-based combat. If each controller implements its own movement, attack, and turn-ending rules, fixes can reach one path while leaving the other inconsistent. Automated tests can then exercise behavior that differs from the playable game.

The requirement was to vary how an action is chosen while keeping its validation and execution consistent. Combat also needs to handle asynchronous input, movement and attack sequences, unit death, and victory or defeat without leaving the state machine waiting indefinitely.

  • Keep combat state and board mutation under shared ownership.
  • Allow either side to be AI-controlled without duplicating gameplay rules.
  • Use the real combat scene for unattended, complete-match smoke tests.

2. Competing architectural approaches

Three approaches illustrate the design trade-offs. This comparison describes the architecture's alternatives; it does not imply each was separately prototyped.

Where to put combat execution rules
Approach Trade-off
Separate human and AI execution Direct to implement initially, but duplicates validation and creates opportunities for rules to diverge.
Controllers mutate the board directly Gives controllers flexibility, but allows them to bypass the state machine's action and transition rules.
Shared execution, separate decisions Centralizes the rules, but requires a controller interface, an input bridge, and careful sequencing of asynchronous actions.

3. Decision and trade-offs

The implemented design separates action selection from execution. Each side has an ICombatController. A human supplies decisions through input and menus; an AI produces intents that are translated into the same state-machine input verbs. Combat states validate actions, and CombatManager owns board mutation.

The cost is coordination. An AI must wait for movement or an attack sequence to settle before sending the next intent. The bridge also depends on the input vocabulary of the states, so changes to interaction flow need review in both human and AI paths.

4. Implementation and responsibilities

HumanController participates in the common interface while the active state waits for input. AIController reads a board view, asks a decision strategy for a plan, and passes intents to ControllerInputBridge. The bridge invokes the live state's movement, attack, and wait actions instead of applying combat results itself.

States own activation flow. Movement and attack intents await the corresponding state's settled signal; guards stop further AI input if combat has ended, the acting unit has died, or its activation has finished. This matters when a counterattack kills the attacker before its planned turn is complete.

I use AI extensively during implementation. My active responsibilities include defining requirements, making architecture decisions, reviewing proposed changes, investigating behavior, and validating results. This project reflects that workflow; it should not be read as a claim that I manually authored every line.

The same delivery responsibilities extend beyond architecture: the public alpha was shown at PlayNYC, and subsequent player feedback informed readability and UI improvements. See the published PlayNYC feedback update.

5. Automated AI-versus-AI testing

With AI controllers on both sides, the smoke harness can play complete matches through the real CombatScene bootstrap. The CI smoke check runs 20 simulations, rotating the authored demo encounters, and checks that every fight reaches a valid victory or defeat within its timeout.

  • Reset session state between matches and isolate late callbacks using a per-run identifier.
  • Report timeout, invalid outcome, and bootstrap failures distinctly.
  • Expose the result through a pass/fail sentinel and process exit status for CI.

The harness targets failures such as non-termination and stalled activations. Project testing notes also document a counterattack-death freeze found using generated encounters, illustrating why varying encounter coverage matters beyond repeating the demo rotation.

Twenty completed simulations are a smoke check for those runs. They do not prove game balance, comprehensive correctness, or coverage of every roster and state transition. Fast simulation also skips presentation timing, so a passing run cannot validate animation pacing or input feel.

6. Observed benefits and limitations

The implementation gives both decision sources a common path for movement, attacks, and activation completion. Full-match automation exercises that path without a person playing each fight. Decision strategies can change while the execution rules stay in the shared combat layer.

This is a structural benefit, not a measured claim about development speed or defect reduction. Shared code can still contain shared bugs. Repeating the same deterministic encounter adds little new coverage, and an AI-driven test does not reproduce a human exploring menus, cancelling actions, or using a controller.

Focused automated tests and manual playtesting remain necessary. Network control is a possible extension of the interface, not a shipped capability claimed by this case study.

7. Lessons learned

  • Make the validation boundary explicit: a controller chooses an action; shared gameplay code decides whether and how it happens.
  • Treat asynchronous completion and terminal-state guards as part of the contract, particularly when an actor can die during its own action.
  • Design test results around a specific question. Here, “did every fight terminate?” is useful and narrower than “is combat correct?”
  • Use player feedback for questions automation cannot answer, including readability, navigation, and feel.
  • In an AI-assisted workflow, clear requirements, critical review, and independent validation remain active engineering responsibilities.
